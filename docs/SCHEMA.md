# Обновление схемы

`UpdateAsync(CancellationToken)` предназначен для старта приложения. Это отдельный
ограниченный механизм обновления поверх метаданных и SQL-генераторов EF Core.
Он не вызывает `EnsureCreated` или `Migrate` и не генерирует исходники миграций.

## Алгоритм

1. EF строит модель и операции создания полной схемы выбранного провайдера.
2. Открывается отдельное соединение; берётся блокировка обновления.
3. Читается `__TrexonDataHistory`. Для управляемых таблиц сверяются физическая
   структура и сохранённые определения. Новая управляемая таблица не должна
   существовать без истории.
4. Проверяются неизменность уже применённых `Change` и поддержка всех операций.
   Неподдерживаемые операции не выполняются частично на этапе планирования.
5. Генерируется SQL провайдера. Для существующих таблиц применяются явные изменения,
   затем автоматические добавления. Новые таблицы создаются по конечной модели.
6. Выполняется SQL. В SQLite дополнительно проверяется `foreign_key_check`.
7. Сохраняются снимок модели, физические определения и история. Снимается блокировка.

`SchemaUpdateResult` содержит `Changed`, `OperationCount`, `AppliedChanges`.
Количество операций — число операций EF, а не SQL-команд или изменённых строк.
Все публичные операции ввода-вывода поддерживают отмену.

## История и повторы

В таблице истории одна строка `current` хранит актуальный снимок, а строки
`update-<guid>` — успешные обновления с временем UTC. Снимок содержит версию формата,
провайдера, сопоставления колонок, ключей, ограничений, индексов и хеши именованных
изменений. Это служебные данные библиотеки; изменять их вручную нельзя.

Повторный вызов при неизменной модели не выполняет DDL управляемых таблиц.
Проверка наличия служебной таблицы выполняется при каждом старте.
Новая база сразу получает конечную модель. Старые `Change` отмечаются применёнными,
а не воспроизводят старые промежуточные схемы.

Сохраняйте каждое применённое изменение без редактирования и в исходном порядке.
Переименование, например, использует физические имена:

```csharp
config.Change("001-name", c => c.RenameColumn("Users", "Name", "FullName"));
config.Change("002-legacy", c => c.DropColumn("Users", "Legacy"));
config.Change("003-length", c => c.AlterColumn("Users", "FullName"));
config.Change("004-score", c => c.AddRequiredColumn("Users", "Score", 0));
```

Текущая EF-модель должна соответствовать результату изменений. `AlterColumn`
использует параметры конечной модели. Несколько последовательных переименований
могут применяться за один запуск. Изменения, которым нужен отсутствующий в конечной
модели промежуточный столбец, отклоняются; полноценного языка миграций здесь нет.
Если таблица отсутствует в предыдущем снимке, исторические операции для неё
не исполняются: она создаётся сразу по актуальной модели.

Значение `AddRequiredColumn` должно быть JSON-сериализуемой константой, совместимой
с типом колонки провайдера. Value converters со сложными пользовательскими типами
могут требовать default в EF-модели вместо этого метода. Временный default нужен
только для заполнения; после добавления он удаляется, если не указан в модели.
Для обязательного поля с `HasDefaultValue` / `HasDefaultValueSql` явный Change
не обязателен. Генерируемую identity-колонку в старую таблицу добавлять нельзя.

## Связи между сущностями

Все три кардинальности и пример с `Include` описаны в
[руководстве по связям](RELATIONSHIPS.md). При создании новых таблиц EF формирует
их связи. Добавление или изменение FK в уже существующей таблице отклоняется.
Новая таблица связи М:М поддерживается, если собственные ограничения существующих
таблиц не меняются. Циклические зависимости, которые требуют отдельной
`AddForeignKeyOperation` после создания таблиц, пока отклоняются.

## Блокировки и ошибки

- PostgreSQL: advisory lock на уровне БД и транзакция DDL + истории.
- SQLite: записывающая транзакция сериализует обновления. Foreign keys временно
  отключаются только на соединении обновлятора до транзакции для перестройки
  таблиц; перед фиксацией выполняется `foreign_key_check`, после FK включаются.
- MySQL: именованная блокировка соединения, отдельная для каждой базы, ожидание
  до 30 секунд. DDL вызывает implicit commit, поэтому перед ним записывается
  durable pending-маркер. История успешного обновления фиксируется транзакционно.

После сбоя PostgreSQL/SQLite транзакция откатывается. После частичного сбоя MySQL
новый запуск останавливается с понятной ошибкой. Восстановление — возврат к известной
исправной БД вместе с её соответствующей историей. Автоматического отката MySQL-DDL
или метода «подтвердить повреждённую схему» нет.

Блокировки не блокируют обычные сессии приложения и не обеспечивают совместимость
старой и новой версий приложения. Завершите обновление до запуска рабочих процессов.
Соединения должны указывать на основной сервер; режим read-only для обновления
схемы не подходит.

## Проверка ручных изменений

SQLite: сохраняются определения таблицы, индексов и триггеров из `sqlite_master`.
PostgreSQL: колонки, defaults, identity/generated, collation, индексы, ограничения,
пользовательские триггеры. MySQL: `SHOW CREATE TABLE` без меняющегося счётчика
`AUTO_INCREMENT`. При расхождении обновление останавливается.
Это проверка управляемых объектов, а не общий аудит БД, прав и внешних зависимостей.

## Что отклоняется

- Переименование/удаление таблиц; удаление/изменение существующих индексов.
- Изменение PK/FK/unique/check-ограничений существующей таблицы.
- Удаление индексированной колонки или колонки, связанной с ограничением.
- Изменение типа PK/FK; nullable → required без отдельного механизма backfill.
- Последовательности, `HasData`, произвольные SQL-миграции и операции вне разрешённого набора.
- Подхватывание существующей таблицы без истории Trexon.Data.
- Изменения параметров БД, например charset после первого создания модели.

При переименовании индексированной колонки сохраните стабильное имя индекса
в EF-модели; изменение его конвенционного имени считается заменой индекса.
SQL check-выражения не переписываются автоматически.

Для PostgreSQL/MySQL сама база создаётся инфраструктурой. Для PostgreSQL схемы,
указанные в модели, создаются EF-операцией `EnsureSchema`. Для SQLite схемы не
поддерживаются провайдером. Возможности типов данных и LINQ ограничены провайдером
и сервером; библиотека не делает три движка полностью взаимозаменяемыми.
